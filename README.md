# 高等教育ニュースポータル

神戸大学、国立大学、高等教育政策・予算、認証評価、法人評価、文部科学省、
入試・就職・大学ランキングなどの公開ニュースを自動収集し、閲覧者自身が
必要な記事を探せるようにする個人運営の情報整理アプリです。収集処理と公表画面を分離し、
公表画面は保存済みの公開用データだけを読み込みます。

公開サイト：<https://kobe-higher-education-news.streamlit.app>

## 現在できること

- 13の情報源・ニュース検索を毎日朝8時頃に1回だけ更新
- 収集担当はSQLiteへ履歴を保存し、公表用JSONを生成
- 公表画面は外部サイトへ収集に行かず、公開用JSONだけを読み込む
- SQLiteデータベースへの重複を除いた保存
- 新聞・雑誌・Googleニュース経由の記事は公表画面で概要を非表示
- 公的機関と正式RSSが配信する概要は公表画面で活用
- 公開日時（不明時は初回取得日時）が3日以内の記事に赤い「NEW!」を表示
- NEW記事の主語別件数・タイトル一覧・URLを画面上部に表示し、テキストでも保存
- 4つの主語＋「すべて」の記事数・公開3日以内の記事数・媒体数を一覧表示
- 赤・橙・黄・青・紫の行タイトルをクリックして記事一覧を絞り込み
- 神戸大学関係を起動時に選択
- 媒体、期間（1日～365日・全期間）、キーワードによる絞り込み
- 「すべて」を初期値とするテーマによる横断的な絞り込み
- 無料・有料・不明の推定分類
- 1つの情報源が失敗しても、ほかの取得を継続
- 取得失敗と件数の記録
- ダークテーマ、標準文字サイズ13px、コンパクトなサイドバーによる表示
- Google Analyticsによる、個人を直接特定しない公開サイトの利用状況確認

担当者による掲載可否の判断や所見の入力は必要ありません。自動分類は記事を
削除するためではなく、探しやすくするために使用します。

- 神戸大学／Kobe University
- 国立大学の予算・政策・改革・評価
- 高等教育の政策・予算
- 認証評価・法人評価・内部質保証
- 大学入試・就職・ランキング

## データベースに保存する内容

`02_output/higher_education_news.db` はSQLite形式のデータベースです。
記事本文の保管庫ではなく、ニュースを探すための索引として次を保存します。

- 記事タイトル
- 元記事を開くためのURL
- 元サイトが公開している短い概要
- 媒体名と取得方式（RSS、公開記事一覧など）
- 記事の公開日時
- 初めて取得した日時と、最後に確認した日時
- 従来の5分野分類、関連度、神戸大学関係かどうか
- 画面用の主語分類と、記事に0個以上付くテーマ
- 無料、有料の可能性、無料・有料不明の推定
- 一般ニュース検索で使用した検索条件
- 重複を判定するために正規化したタイトル

公式RSSや専門媒体では元記事のURLを保存します。一般ニュース検索では、
検索サービスを経由して元記事を開くURLになる場合があります。

別の表には、記事と複数テーマの対応、情報源ごとの更新開始・終了日時、成功・失敗、
取得件数、新規件数、エラー内容を保存します。また、分類ルールの版番号も保存します。
従来の分類列は削除・上書きせず残しているため、今回の方式から戻すこともできます。

記事本文、有料部分、パスワード、APIキー、個人情報は保存しません。

## 収集データと公表データの分離

収集担当は `higher_education_news.db` に取得履歴、概要、分類、取得結果を保存します。
公表画面はSQLiteへ接続せず、収集後に生成する `public_news.json` だけを読み込みます。

公表用JSONには、高等教育との関連度がある記事を出力します。
無料・有料の推定結果は参考情報として保持しますが、掲載の可否には使用しません。
神戸大学、文部科学省、公的機関の概要と、各サイトが正式RSSで配信した概要は活用します。
新聞・雑誌・Googleニュース検索経由の記事は、分類には概要を利用しても、公表用JSONでは
概要を空欄にして、タイトル、媒体名、日付、分類、元記事へのリンクを表示します。

## 文部科学省記事の概要

文部科学省のRSSには、記事タイトル・日付・URLはありますが、記事概要が入っていません。
このため、データベースに概要がない記事だけ公式ページを開き、公開された本文冒頭から
最大400文字を補います。連絡先、委員名簿、PDF閲覧案内などは概要に使いません。
適切な説明文が見つからない場合は、内容を推測せず「文部科学省が情報を公開した」
という短い案内文を表示します。一度保存した概要があれば、更新のたびに同じページを
開かないため、表示速度と文部科学省サイトへの負荷を抑えます。

## NEW表示

公開日時が画面を開いた時点から3日以内の記事に、赤い「NEW!」を表示します。
公開日時を取得できない記事は、初めてデータベースに保存した日時を代わりに使います。
ちょうど3日前の記事はNEWに含み、3日を超えると自動的に表示が外れます。

画面上部の「NEWタイトル一覧を開く」には、現在NEW表示の付く記事を4つの主語別に
まとめて表示します。「NEW概要をテキスト保存」では、記事タイトル、元記事URL、
ニュースサイトURLを含む共有用の下書きを保存できます。

## 一日一回のメール配信（次の段階）

自動メールはまだ送信しません。毎日同じ記事を繰り返さないよう、メール版では
「公開3日以内」ではなく「前回の正常送信後に初めて取得した記事」を対象にします。
想定する流れは次のとおりです。

1. Windowsのタスクスケジューラなどで一日一回ニュースを更新
2. 前回送信後の新規記事を主語別にまとめる
3. 件数、タイトル、元記事URL、共有ニュースサイトURLを1通のメールにする
4. 正常送信した日時と件数をデータベースへ記録

共有ニュースサイトには、公開済みの
`https://kobe-higher-education-news.streamlit.app` を使用します。メール機能の実装前に、
承認された送信方法（Microsoft 365／Outlookなど）を決めます。パスワードや認証情報は
ソースコードやデータベースへ保存しません。

## ニュースを更新する

閲覧画面から収集処理と手動更新ボタンを取り除いています。閲覧者が画面を開いても、
神戸大学、文部科学省、各媒体、Googleニュースへのアクセスは発生しません。

手元で収集用SQLiteと公表用JSONを更新する場合は、PowerShellで次を実行します。

```powershell
python .\03_scripts\collect_news.py
```

Streamlit Community Cloud向けには `.github/workflows/daily_news.yml` を用意しています。
GitHub Actionsは協定世界時で動くため、`23:00 UTC` を指定し、日本時間の翌朝8時頃に
1日1回収集します。1媒体が失敗しても、取得できた情報源の公表データは生成します。
GitHubへ登録後は、Actions画面の `Run workflow` から手動実行して動作確認もできます。
日次処理では `--allow-partial` を使い、失敗した媒体をログへ残しながら、取得できた
媒体の更新結果を正常に公開します。

### 大学ジャーナルオンラインをPCから補完する

GitHub Actionsから大学ジャーナルオンラインのRSSへアクセスすると、現在はHTTP 403で
拒否されます。一方、PCからは取得できるため、必要に応じて次を実行します。

1. `03_scripts/publish_university_journal.cmd` をダブルクリック
2. 最初の確認で `Y` を入力
3. GitHubの既存件数、PCでの取得件数、新規候補タイトルを確認
4. 公開してよい場合だけ `PUBLISH` を入力
5. `Completed` と公開サイトURLが表示されることを確認

構文検査、単体テスト、GitHubの競合確認がすべて成功した場合だけ公開用JSONを更新します。
失敗時や確認を中止した場合はGitHubを変更しません。新規補完記事は本文やRSS概要を公開せず、
タイトル、媒体名、日付、分類、元記事リンクだけを追加します。SQLiteは更新しませんが、
公開用JSONは既存記事を引き継ぐため、補完記事は翌朝の自動更新後も保持されます。

GitHub Actionsとの競合を避けるため、朝8時30分以降の実行を推奨します。頻度の目安は、
重要度を優先する場合は平日1日1回、負担を抑える場合は週1～3回です。

## 閲覧画面を起動する

PowerShellのスクリプト実行制限に影響されない、次のコマンドを推奨します。

```powershell
python -m streamlit run .\03_scripts\app.py
```

## 主語別サマリー表とテーマ

記事を「誰・どの組織の話か」という主語と、「何についての話か」というテーマの
二軸で整理します。起動時は主語「神戸大学関係」、テーマ「すべて」を表示します。

### 主語別サマリー表

- 神戸大学関係
- 文部科学省関係
- 国立大学関係
- その他の大学・高等教育機関
- すべて：4つの主語をまとめて確認する場合に使用

大学改革支援・学位授与機構の記事は「その他の大学・高等教育機関」に入ります。
国立大学の記事は、国立大学協会の2026年4月1日現在の会員名簿を基礎にした大学名でも
判定します。5つの行を選択しなくても、「記事」「うち、公開3日以内」「媒体数」を
同時に比較できます。表示順は「すべて」「文部科学省関係」「神戸大学関係」
「国立大学関係」「その他の大学・高等教育機関」です。行タイトルは赤・橙・黄・青・紫の
濃い背景色で区別し、クリックするとその主語の記事だけを表示します。選択中の行には
チェック印と二重枠を付け、未選択の行は少し薄く表示します。表の件数は、期間・テーマ・
媒体・キーワードなど現在の条件を反映します。左側の媒体候補も、期間・キーワード・テーマ・
現在選択中の主語に該当する媒体だけに自動で切り替わります。

### テーマ

右側の主画面で、主語別サマリー表のすぐ上にあるテーマ欄から次のいずれかを選びます。
主語別サマリー表とテーマを近くに置き、「誰の話か」と「何の話か」を続けて指定できます。
左側は、更新、キーワード、媒体、期間という補助的な条件に限定します。

- すべて：テーマで絞り込まない初期状態
- 政策・制度・予算
- 入試
- 学生支援・就職支援・キャリア教育
- 教育
- 研究
- 国際・留学生
- 評価・質保証
- 社会連携・地域貢献

1記事には複数テーマを付けられます。例えば、国立大学の認証評価記事は
「国立大学関係」の行に入り、「評価・質保証」テーマでも見つかります。
大学改革支援・学位授与機構の認証評価記事は「その他の大学・高等教育機関」の行に入り、
同じ「評価・質保証」テーマで見つかります。テーマが付かない記事も削除せず、
テーマ「すべて」では表示します。大学ランキングは専用テーマを設けず、
当面は「すべて」またはキーワード検索で確認します。

## 初期表示の考え方

初期画面では次の条件を使います。

- 主語「神戸大学関係」
- テーマ「すべて」
- 直近7日（1日、3日、7日、14日、30日、90日、365日、全期間から変更可能）
- 高等教育との関連度がある記事だけ
- 公開日時の新着順

関連度条件と並び順は固定し、画面上のスイッチやラジオボタンは表示しません。
無料・有料の推定結果にかかわらず、関連度がある記事は通常画面に表示します。
「関連度が低い候補」は通常画面には表示しません。右側のテーマと、左側の期間・媒体・キーワードは
引き続き変更できます。

## 有料記事判定の限界

有料記事の判定は、媒体名と「会員限定」などの表示に基づく推定です。
一覧では無料でも、記事の途中から有料になる場合があるため、完全な判定はできません。
判定結果は `無料と推定`、`有料の可能性`、`無料・有料不明` の3種類です。
この判定結果は画面上の参考情報として表示しますが、記事の掲載条件には使用しません。

有料部分を回避して取得する処理は実装していません。

## 著作権・情報セキュリティ

- 記事本文をデータベースへ保存しない
- 公開されたタイトル、短い概要、URL、媒体名、日付だけを収集用データへ保存する
- 公表用データでは新聞・雑誌・Googleニュース経由の記事概要を非表示にする
- 公的機関と正式RSSの公開概要は出典・元記事リンクとともに活用する
- 有料部分やログイン後の内容を取得しない
- 参考メールは読み取り対象とし、元ファイルを変更しない
- 外部AIへ記事本文を送信しない
- APIキーや認証情報をソースコードへ書かない

画面下部には次の注意書きを小さく表示します。

> 本サイトは、公開情報を自動収集・分類した個人運営の情報整理サイトです。詳細・正確な内容はリンク先をご確認ください。分類は自動処理による推定です。

あわせて、Google Analyticsの利用、収集する情報、検索文字を送信しないこと、
Googleのプライバシーポリシーへのリンクを表示します。

## Google Analytics

公開サイトの利用状況を把握し、画面と分類の改善に役立てるため、Google Analytics 4を
使用します。PC版のlocalhostは集計せず、公開サイトだけを計測します。

- アナリティクスアカウント：高等教育ニュースポータル
- プロパティ：高等教育ニュースポータル
- 測定ID：G-L6PJED9H5W
- イベントデータの保持：14か月
- 新しいアクティビティでのユーザーデータのリセット：オフ
- Googleシグナル：オフ
- 広告パーソナライズ：オフ

測定IDはWebページで使用する公開識別子であり、パスワードやAPIキーではありません。
ただし、別のプロパティへ誤送信しないよう、変更時にはGoogle Analyticsのデータストリームと
03_scripts/app.pyの両方を確認します。

標準のページ閲覧、セッション開始、スクロール、外部リンクのクリックに加え、次の操作を
個人情報を含まないイベントとして記録します。

- theme_filter_changed：テーマの変更
- subject_filter_changed：主語の変更
- period_filter_changed：期間の変更
- media_filter_changed：媒体フィルターの変更
- keyword_search_used：検索欄が使われたかどうか
- new_digest_toggled：NEWタイトル一覧の開閉
- new_digest_downloaded：NEW概要の保存

検索文字そのもの、氏名、メールアドレス、職員を識別する情報は送信しません。媒体についても
媒体名ではなく、同時に選択された件数だけを送信します。GA4には次のカスタム定義を登録します。

- カスタムディメンション filter_value：テーマ、主語、期間等の選択値
- カスタム指標 selection_count：媒体フィルターの選択数
- カスタムディメンション has_search_text：検索文字が入力されたかどうか

Google Analyticsの通常レポートや探索へ反映されるまで24～48時間かかる場合があります。
導入直後や改修後は「レポート」→「リアルタイム」でpage_viewと各操作イベントを確認します。

収集用SQLiteはGitHubへ登録せず、公表用JSONだけをStreamlit Community Cloudで使用します。
APIキーや認証情報が必要になった場合は、GitHubやコードへ書かずSecretsへ保存します。

### 毎日の確認

通常は毎朝8時頃のGitHub Actionsに任せます。公開サイト上部の「最終データ更新」または
GitHub Actionsの実行結果を確認します。日次処理は `--allow-partial` を使用するため、
実行結果が緑色でも一部情報源が失敗している場合があります。時々ログに表示される
「情報源○件、失敗○件」と、失敗した媒体名を確認します。

### データの保護

- `02_output/higher_education_news.db` はPC内の全履歴であり、GitHubへ登録しない
- `02_output/public_news.json` だけをGitHubと公開サイトで使用する
- SQLite、`03_scripts`、`.github`、`.streamlit`、READMEを定期的に別の場所へバックアップする
- バックアップはStreamlit、PowerShell、ニュース更新処理を終了してから行う
- Google Driveの同期中に複数のGit操作や別PCからの同時収集を行わない
- Gitのロックエラーが出ても、対象を確認せずにロックファイルを削除しない

### 定期点検

月1回程度、上位の記事を確認し、未来日付、古すぎる記事、分類の偏り、重複、リンク切れ、
有料記事の混入がないかを確認します。誤りを毎回人手で選別するのではなく、同じ傾向が
繰り返される場合だけ取得・分類ルールを調整します。

### アプリを変更するとき

1. 公開済みの `main` から作業ブランチを作る
2. PC版で変更内容を確認する
3. 構文検査と単体テストを実行する
4. 作業ブランチをGitHubへ送ってPull Requestを作成する
5. `main` へマージし、Streamlit公開サイトを確認する

APIキー、アクセストークン、メールパスワード、個人情報はコードやGitHubへ書かず、
必要になった場合はGitHub SecretsまたはStreamlit Secretsを使用します。
